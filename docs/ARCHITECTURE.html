КАК УСТРОЕНО ПРИЛОЖЕНИЕ, В КАКОЙ ЛОГИКЕ ДЕЛАТЬ ДОРАБОТКИ

1. Общая картина

Приложение — классический клиент-сервер, максимально упрощённый для надёжной локальной работы:

БРАУЗЕР — фронтенд: vanilla JS, без фреймворков и без сборки. Отрисовывает экраны, ходит в API через fetch
⇅ HTTP (JSON)
NODE.JS СЕРВЕР — ноль npm-зависимостей, только встроенный node:http. Раздаёт статику, отдаёт банк вопросов, валидирует и сохраняет прогресс
⇅ файловая система
ДИСК — data/ (вопросы и теория, только чтение) + storage/progress.json (прогресс пользователя, чтение/запись)

Ключевой принцип: вся логика изменения данных живёт на сервере (server/progress.js). Фронтенд никогда не решает сам, что записать — он только сообщает события («ответил на вопрос X неправильно», «сдал экзамен с 2 ошибками»), а сервер валидирует и обновляет состояние. Поэтому клиент можно менять как угодно — данные не сломаются.

3. Как живёт фронтенд

Роутинг — адресная строка решает всё

Навигация работает через #hash: #/practice, #/theory/ch3, #/exam… В main.js лежит таблица «регулярка → функция отрисовки». Браузерное событие hashchange вызывает route(), тот находит совпадение и вызывает нужную renderXxx(view).

Пользователь кликает ссылку <a href="#/practice">
↓
Браузер меняет hash → событие hashchange
↓
route() в main.js находит маршрут в таблице
↓
renderPracticeList(view) из views.js перерисовывает <main>

Отрисовка — функции вместо фреймворка

Каждый экран — функция, которая собирает DOM хелпером el() и вставляет в <main> через clear(). Никакого virtual DOM: при изменении данных функция просто вызывается заново. Текст вставляется как текстовые узлы (не innerHTML) — XSS невозможен.

el('div.card', {},                       // тег.класс.класс
  el('h2', {}, 'QUESTIONS MASTERED'),    // дети — узлы или строки
  el('p.stat-value.ok', {}, '124'),
)

Состояние — один объект + кеши

В state.js живёт объект state: снимок прогресса с сервера (state.progress), манифест тем и кеш загруженных вопросов (Map по теме — каждая тема скачивается один раз). После каждой мутации сервер возвращает свежий снимок, и фронт просто заменяет state.progress целиком — никакой ручной синхронизации.

4. Как живёт бэкенд

Один HTTP-сервер с двумя «крыльями»: всё, что начинается с /api/ — обрабатывает handleApi(), остальное — раздача файлов из public/.

API

МетодПутьЧто делает
GET/api/manifestСписок тем (+ это whitelist допустимых slug)
GET/api/questions/:slugВопросы темы (slug проверяется по манифесту)
GET/api/theoryУчебник теории
GET/api/progressСнимок прогресса + посчитанная статистика
PUT/api/progress/profileИмя / язык / тема / онбординг
POST/api/progress/answersПакет ответов (≤100): счётчики, ошибки, стрик
POST/api/progress/examsРезультат экзамена
POST/api/progress/theoryГлава прочитана
DELETE/api/progressПолный сброс

Путь одной записи (ответ на вопрос)

Фронт: api.recordAnswers([{id, correct:false}]) → POST /api/progress/answers
↓
index.js: readJsonBody() — лимит 256 КБ, парс JSON
↓
progress.js: валидация (id — строка, correct — boolean, ≤100 шт.) — иначе 422
↓
progress.js: обновить счётчики, список ошибок, стрик дня
↓
store.js: записать ВО ВРЕМЕННЫЙ файл → атомарно переименовать в progress.json
↓
Ответ: свежий снимок прогресса → фронт кладёт его в state.progress

Почему данные не теряются

  • Атомарная запись: temp-файл + rename — при падении в середине записи старый файл остаётся целым.
  • Очередь записи: записи сериализованы — два одновременных запроса не перемешаются.
  • Карантин: если progress.json повреждён (рукой, диском) — он откладывается в progress.json.corrupt.<время>, сервер стартует с чистого, ничего не перезаписывая.
  • Graceful shutdown: Ctrl+C ждёт, пока очередь записи дойдёт до диска.

5. Модель данных (storage/progress.json)

{
  "profile":   { "name": "Valentin", "language": "ru",
                 "theme": "dark", "onboarded": true },
  "answers":   { "sorpasso-...-0": { "correct": 3, "wrong": 1,
                 "lastCorrect": true, "last": "2026-06-10T…" } },
  "mistakes":  ["segnali-divieto-...-4"],   ← последний ответ был неверным
  "exams":     [{ "date": "…", "total": 30, "errors": 2, "passed": true }],
  "theoryRead":["ch1", "ch2"],
  "streak":    { "current": 5, "lastDay": "2026-06-10" }
}

Производная статистика (mastered, examSuccess…) не хранится — она каждый раз считается в snapshot(). Это исключает рассинхронизацию.

6. Рецепты доработок

РЕЦЕПТ Новый экран

  1. В views.js написать export function renderStats(root) {…} — собрать DOM через el(), вставить clear(root, …).
  2. В main.js добавить строку в таблицу routes: { pattern: /^#\/stats$/, name:'stats', render: () => renderStats(view) }.
  3. Добавить ссылку <a href="#/stats"> в навигацию index.html.

РЕЦЕПТ Новый эндпоинт API

  1. Логика + валидация — метод в server/progress.js (бросать ValidationError на плохой ввод).
  2. Маршрут — ветка в handleApi() в server/index.js.
  3. Клиент — одна строка в public/js/api.js.
  4. Тест — кейс в tests/progress.test.js, прогнать npm test.

РЕЦЕПТ Изменить дизайн

Все цвета, рамки и тени — CSS-переменные в начале styles.css (--ink, --paper, --accent, --shadow…). Тёмная тема — это просто переопределение переменных в блоке [data-theme="dark"]. Меняете переменную — меняется всё приложение.

РЕЦЕПТ Поменять правила экзамена

Константы в начале views.js: EXAM_QUESTIONS, EXAM_SECONDS, EXAM_MAX_ERRORS, PRACTICE_BATCH. Серверная проверка экзамена ограничена только здравым смыслом (total 1–100), так что менять можно свободно.

7. Куда встроятся аккаунты (ваш следующий шаг)

Архитектура к этому готова — точки расширения уже изолированы:

  1. Хранилище: сейчас один JsonStore на единственного пользователя. Для аккаунтов — заменить на SQLite (таблицы users, answers, exams) — меняется только store.js + конструктор ProgressService; вся доменная логика в progress.js остаётся.
  2. Аутентификация: middleware-функция перед handleApi() в index.js: проверка сессионной cookie → userId → ProgressService этого пользователя. Пароли — только хешем (argon2/bcrypt), сессии — httpOnly + Secure cookie.
  3. Регистрация по почте: новые эндпоинты /api/auth/*; для писем понадобится первый внешний сервис (SMTP-провайдер) — его ключи строго в .env, как уже заведено.
  4. GDPR (Италия = ЕС + Garante Privacy): double opt-in подтверждение почты; privacy policy на итальянском до сбора данных; явное согласие (не предотмеченная галочка); минимизация данных (почта + хеш пароля, больше ничего); экспорт своих данных (ст. 15) и удаление аккаунта (ст. 17) — кнопками в Settings; хостинг данных в ЕС; реестр обработки. Фронтенд уже не хранит ничего чувствительного — это правильная база.

8. Инварианты — что нельзя ломать

  • ПРАВИЛО Секреты и конфигурация — только в .env. Никогда в коде, никогда в public/.
  • ПРАВИЛО Фронтенд не решает, что записать — только сервер валидирует и мутирует данные.
  • ПРАВИЛО Пользовательский текст в DOM — только текстовыми узлами (через el()), не innerHTML.
  • ПРАВИЛО Любая запись на диск — через JsonStore (атомарность), не fs.writeFile напрямую.
  • ПРАВИЛО Новая логика прогресса — с тестом в tests/; npm test должен быть зелёным.
