Patente Pro · Architecture

How Patente Pro works.

A trainer for the Italian driving-licence theory exam. It runs two ways from one codebase: as a desktop app with a local server that owns a progress file, and as a hosted web app that a phone installs and keeps its progress inside. The rules that guard every write are the same module in both.

The core idea

Two hosts, one set of rules

The difference between the two modes is only where the write lands. On a computer it lands in a file that the Node server owns; on a phone it lands in that phone's own storage. Everything that decides whether a write is allowed — validation, counters, mistakes, streak — is one module loaded by both.

The interesting mechanism

What happens when you answer a question

In hosted mode the answer is written in the page and there is nothing to fail. In local mode it crosses a network, so the app assumes that hop can break — mid-session, mid-exam — and never loses the answer when it does.

The map

What each part is responsible for

PartResponsibility
public/js/domain/ The rules: validation, answer counters, mistakes, streak, import. Pure JavaScript, no imports — which is why it runs on the server and in the phone alike.
server/ An HTTP server on node:http: routing, the progress file (written to a temp file then renamed, so a crash cannot corrupt it), a corrupt file quarantined rather than wiped, path-traversal protection, and a bind to 127.0.0.1.
public/js/ The whole interface: a hash router, screens, the offline queue, sounds. No framework and no build step — the files the browser loads are the files in the repository.
public/sw.js The service worker. Code is network-first so updates land immediately; study content is served from cache and refreshed behind you, which is what makes the app work with no connection.
data/ Read-only content: 7139 questions in 26 topics, the theory manual, the lessons, the dictionary, and all 413 sign images — nothing is fetched from anyone else at runtime.
bin/ The desktop launcher: picks a free port, starts the server, waits for it to answer, then opens a chromeless window so it behaves like an installed application.
scripts/build-static.js Assembles dist/ for hosting and stamps the marker that puts the frontend into phone mode. Used only when deploying; local development stays build-free.
Where your progress lives

One file, or one phone

Progress is never mixed between machines and never sent anywhere. Moving it is deliberate: export a backup file, import it on the other device — the same validated path an app update uses.

Constraints held on purpose

The rules that keep it simple

No dependencies

Nothing to install, nothing to audit, nothing that breaks in two years. CI fails the build if a dependency ever appears.

One place mutates data

Every change goes through the domain module. A screen can only report what happened; it cannot invent state.

Writes are atomic

Progress is written to a temp file and renamed. A crash mid-write leaves the previous file intact, never half of one.

Text is text

Question text reaches the page as text nodes, never as HTML, so content can never become markup.

The exam is the exam

30 questions, 20 minutes, 3 errors — the official format, with the translation hidden until you ask for it.

Offline is normal

Images and questions are local, the shell is cached, and answers given with no connection queue and sync later.

Publishing it

What turns this into a phone app

  1. A host runs node scripts/build-static.js and serves dist/ — 458 files, 8.1 MB, no server process.
  2. The build stamps the standalone marker, so the frontend keeps progress in the phone instead of calling an API that isn't there.
  3. HTTPS makes the service worker legal, so the phone offers Add to Home Screen and the app opens without browser chrome.
  4. After the first load the question bank is cached: the app keeps working on the metro with no signal.
